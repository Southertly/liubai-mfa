# 留白 MFA Windows 二维码与 Google Authenticator 导入规格

日期：2026-08-13

目标平台：Windows 11 x64

技术栈：WinUI 3、C#、.NET 8、Windows App SDK、MSIX

状态：设计已确认

## 1. 背景

Windows MVP 已能从 PNG、JPEG 或 BMP 文件中识别单个标准 `otpauth://totp` 二维码，但还不能直接框选屏幕、读取剪贴板截图，也不能解析 Google Authenticator 的 `otpauth-migration://` 转移二维码。现有 TOTP 实现固定为 SHA-1、6 位、30 秒，无法完整导入 Google 转移数据中的高级 TOTP 参数。

本功能在不引入云服务、不修改其他平台分支的前提下，统一 Windows 端的截图、剪贴板和图片导入，并支持 Google Authenticator 单张及多张转移二维码。

## 2. 目标

1. 从 Windows 11 原生矩形截图结果识别二维码。
2. 从用户明确触发的剪贴板读取操作中识别截图二维码。
3. 保留并完善本地图片二维码导入。
4. 自动区分标准 `otpauth://totp` 和 Google `otpauth-migration://`。
5. 支持 Google Authenticator 单张和多张、乱序及重复扫描的转移批次。
6. 支持 SHA-1、SHA-256、SHA-512、6/8 位和自定义周期的 TOTP。
7. 在写入前统一展示新增、重复、暂不支持和无效账户。
8. 以一次加密保存完成批量导入；失败时不留下半批账户。

## 3. 非目标

- 不支持 HOTP；Google 转移数据中的 HOTP 必须明确标记为暂不支持。
- 不支持 MD5 或未知算法，也不得自动降级为 SHA-1。
- 不实现摄像头实时扫码。
- 不后台监听剪贴板。
- 不自行实现全屏 Direct3D 捕获和框选遮罩。
- 不修改 Android 或 HarmonyOS 分支。
- 不修改 v2 备份的加密外层格式。
- 不将二维码、账户或导入统计上传到网络。

## 4. 方案选择

采用 Windows 11 新版截图工具协议：应用通过 `ms-screenclip://capture/image` 请求矩形截图，截图工具通过应用注册的专用协议回调返回结果。当前项目为 MSIX 打包应用，符合安全回传所需的应用身份条件。

不采用自建 `Windows.Graphics.Capture` 框选界面，因为它会额外引入 Direct3D、HDR、多显示器、DPI 和窗口排除问题。不采用启动旧截图协议后轮询剪贴板的方式，因为无法可靠区分旧图片、取消操作和新截图。

图片、剪贴板和截图回调进入同一解码与导入管线，避免三个入口出现不同验证规则。

## 5. 用户入口

主界面顶部保留两个紧凑命令：

- 添加账户；
- 导入二维码。

“导入二维码”打开 `MenuFlyout`，包含：

1. 截图识别二维码；
2. 从剪贴板识别；
3. 从图片导入。

三个入口必须提供简体中文工具提示、可朗读名称和键盘焦点。Google Authenticator 不单独占用主界面按钮；二维码内容解析后自动进入对应流程。

## 6. 截图流程

### 6.1 发起截图

1. 应用确认新版截图协议可用。
2. 为本次请求生成不可预测的关联 ID。
3. 通过 `Launcher.LaunchUriAsync` 发起矩形截图，只启用图像捕获能力。
4. 应用进入失活状态，继续遵守原有 1 分钟自动锁定规则。
5. 用户完成或取消后，截图工具通过专用回调协议重新激活应用。

MSIX 清单注册只供本应用使用的回调协议。应用只接受当前有效请求的关联 ID；过期、重复或无法匹配的回调不进入解析流程。

### 6.2 返回与锁定

- 用户取消截图时返回主界面，不显示错误。
- 截图协议不可用时，提示改用剪贴板或图片导入。
- 若截图期间超过自动锁定时限，应用返回后先显示锁定界面；Windows Hello 成功后才读取并解析截图结果。
- 回调结果不应在锁定界面展示文件名、缩略图、二维码类型或账户数量。
- 应用不将返回图片复制到自己的数据目录，也不创建长期缓存。

## 7. 剪贴板与图片流程

### 7.1 剪贴板

- 仅在用户点击“从剪贴板识别”后读取一次剪贴板。
- 只接受位图内容；普通文本、文件列表或 HTML 不作为二维码来源。
- 剪贴板没有图片时提示“剪贴板中没有可识别的图片”。
- 应用不清空或改写用户剪贴板。

### 7.2 本地图片

- 使用现有 Windows 文件选择器。
- 支持 PNG、JPEG、JPG 和 BMP。
- 用户取消选择时静默返回。
- 沿用并统一文件大小、像素尺寸和总像素数量限制。

## 8. 统一图片解码

`QrImageDecoder` 接受受控的图像源并返回单个二维码文本。所有来源执行相同检查：

1. 验证图片格式和可解码性；
2. 限制文件或内存大小；
3. 限制宽、高和总像素数；
4. 统一转换为 BGRA8；
5. 使用 ZXing QR 模式、自动旋转和强化识别；
6. 限制单次解码耗时和内存占用；
7. 失败时只返回克制的原因，不输出二维码原文。

一张图片只消费一个导入二维码。若画面内存在多个二维码且无法唯一确定，提示用户重新框选单个二维码，避免导入错误对象。

## 9. URI 分流

`OtpImportParser` 只接受：

- `otpauth://totp/...`；
- `otpauth-migration://offline?data=...`。

其他协议、主机、类型或空内容均拒绝。URI 文本和查询参数有明确长度上限。解析结果不写日志。

## 10. 标准 TOTP URI

标准 URI 支持：

- `secret`：必需，Base32；
- `issuer`：可选；
- 标签中的服务和账户；
- `algorithm`：SHA1、SHA256、SHA512，默认 SHA1；
- `digits`：6 或 8，默认 6；
- `period`：正整数，默认 30 秒，并限制到合理范围。

URI 主机必须是 `totp`。`hotp`、缺失密钥、非法 Base32、冲突标签、未知算法、非法位数和异常周期均不能进入保存流程。

单个标准 URI 解析成功后进入账户确认页，用户可确认或修正服务、账户和分组，但不能通过界面改变二维码携带的算法、位数和周期。

## 11. Google Authenticator 转移格式

Google 转移二维码使用 URL 编码和 Base64 包装的 Protobuf `MigrationPayload`。该格式没有稳定的 Google 官方公开规格，因此解析器必须隔离在单独组件中，并以固定测试样本约束兼容行为。

实现使用成熟的 Protobuf 运行库解析本地维护的最小消息架构，不手写无边界的通用二进制解析器。只读取以下字段：

- 账户密钥；
- 名称；
- 服务名称；
- 算法；
- 位数；
- OTP 类型；
- HOTP 计数器；
- 版本；
- 批次数量；
- 批次索引；
- 批次 ID。

HOTP 计数器只用于识别并把该账户标记为暂不支持，不写入本地账户模型。

### 11.1 字段映射

- TOTP + SHA1/SHA256/SHA512 + 6/8 位：可导入。
- Google 迁移格式未携带周期时使用 30 秒。
- HOTP：暂不支持。
- MD5、未定义算法、未定义位数、未定义类型：无效或暂不支持，不自动猜测。
- 服务名称为空时，从名称中的 `服务:账户` 形式提取；仍无法得到服务名称时允许用户在预览页补充。
- 空账户名、空密钥或不能生成验证码的密钥：无效。

## 12. 多批次会话

`MigrationBatchSession` 只在内存中保存当前 Google 导入会话的解析结果和最少批次元数据。

规则：

1. 第一张二维码确定批次 ID 和批次数量。
2. 后续二维码可通过截图、剪贴板或图片任一入口加入。
3. 批次索引可以乱序。
4. 相同批次 ID、总数和索引的重复内容不重复计数。
5. 相同索引但内容不一致时中止并提示批次冲突。
6. 不同批次 ID 或不同批次数量不能混入当前会话。
7. 索引必须落在有效范围且最终完整覆盖全部批次。
8. 收齐前不写入账户仓库。
9. 用户取消、应用锁定、会话超时或进程结束时清除会话。
10. 批次数量、单批账户数和总账户数均设安全上限。

收集界面显示“已读取 X/Y 张”，并提供：

- 继续截图；
- 从剪贴板读取；
- 选择下一张图片；
- 取消导入。

界面不得显示二维码原文或密钥。

## 13. 导入预览

所有批次收齐后生成一次预览。每个账户显示：

- 服务；
- 账户；
- TOTP；
- 算法；
- 位数；
- 周期；
- 状态。

状态分为：

- 新增；
- 重复；
- 暂不支持；
- 无效。

预览顶部显示四类数量。用户可以给可导入账户统一选择分组，并可修正缺失的服务名称。重复、暂不支持和无效账户不能勾选保存，但必须能查看不含秘密的原因。

只有用户点击“导入可用账户”后才保存。没有可导入账户时禁用主按钮。

## 14. 去重与原子保存

TOTP 账户身份由规范化后的以下元组判断：

- 密钥；
- 算法；
- 位数；
- 周期。

去重同时覆盖现有账户和本次批次。仅比较密钥会误判不同参数的有效账户，因此必须升级现有去重逻辑。

批量导入采用候选快照：

1. 从当前账户构建候选集合；
2. 添加所有通过验证且不重复的账户；
3. 一次性加密并保存完整候选集合；
4. 保存成功后再替换内存集合并刷新界面；
5. 保存失败时保留原账户集合并显示错误。

不得出现内存中已添加、磁盘保存失败或只保存部分批次的状态。

## 15. TOTP 模型扩展

`MfaAccount` 增加向后兼容的可选字段：

- `algorithm`：`sha1`、`sha256`、`sha512`；
- `digits`：6 或 8；
- `period`：正整数秒数。

缺失字段继续解释为 SHA-1、6 位、30 秒。默认参数的旧账户在重新保存时可以继续省略这些字段，减少对旧客户端的影响。

`TotpService` 根据账户参数选择 HMACSHA1、HMACSHA256 或 HMACSHA512，并使用 6 位或 8 位模数。剩余时间和进度线按账户周期计算。

v2 备份的加密外层和认证方式不变，内部账户 JSON 可包含上述可选字段。Windows 新版必须读取旧备份。包含高级参数的新版备份在旧 Android/HarmonyOS 客户端中可能无法正确使用；导出这类备份时必须显示兼容性提示，当前 Windows 分支不修改其他平台。

## 16. 组件边界

### 16.1 平台层

- `SnippingToolCaptureService`：发起截图、生成关联 ID、处理回调元数据。
- `ClipboardImageService`：按用户请求读取一次图片。
- `NativeFileService`：选择本地二维码图片。
- `QrImageDecoder`：统一图像校验和 ZXing 解码。

### 16.2 核心层

- `OtpImportParser`：URI 分流和标准 TOTP URI 解析。
- `GoogleMigrationParser`：有边界的 Protobuf 映射。
- `MigrationBatchSession`：批次一致性和生命周期。
- `ImportClassifier`：验证、去重和预览状态分类。
- `TotpService`：多算法、多位数和多周期计算。

### 16.3 界面层

- 导入菜单；
- Google 批次收集对话；
- 批量导入预览；
- 普通账户确认页；
- 紧凑 `InfoBar` 状态反馈。

解析器和分类器不得直接访问 WinUI 控件；平台图像对象在进入核心层前转换为受控字节或二维码文本。

## 17. 激活与实例管理

截图回调可能通过协议激活应用。应用入口必须区分普通启动与截图响应：

- 普通启动继续创建或激活主窗口；
- 截图响应与当前有效关联 ID 匹配后交给截图服务；
- 存在已有主实例时，将响应重定向到主实例处理；
- 新实例不得单独解密账户或显示第二个主窗口；
- 未知协议参数、外部伪造回调和过期回调直接拒绝。

该流程必须与自动锁定共同测试，不能为了截图回调绕过 Windows Hello。

## 18. 错误与状态文案

- 用户取消：“不提示错误，返回验证码列表”。
- 剪贴板无图片：“剪贴板中没有可识别的图片”。
- 图片无二维码：“图片中没有可识别的 MFA 二维码”。
- 协议不支持：“此设备暂不支持直接截图，请使用剪贴板或图片导入”。
- 批次不一致：“这张二维码不属于当前 Google 导入批次”。
- 批次重复：“这张二维码已读取”。
- HOTP：“此账户为 HOTP，当前版本暂不支持”。
- 无可导入账户：“没有可导入的新 TOTP 账户”。
- 保存失败：“账户未导入，本地数据保持不变”。

错误不得包含二维码原文、Base64、Protobuf 字节、密钥或验证码。

## 19. 安全限制

- 截图、剪贴板图片和二维码文本只保存在完成当前操作所需的内存范围内。
- 不将截图保存到应用数据目录。
- 不记录二维码原文、Protobuf、密钥、验证码或账户导入正文。
- 导入完成、取消、锁定、超时或异常时释放批次和图像对象。
- 限制图像字节数、像素数、二维码文本长度、解码后 Protobuf 长度、字段长度、密钥长度、批次数和账户总数。
- Base64、URL 解码和 Protobuf 解析采用失败关闭策略。
- 只允许受支持的 TOTP 参数组合，禁止自动降级。
- 截图回调通过关联 ID、协议参数校验和主实例路由防止混淆。
- 所有处理均在本机进行，不新增远程 API。

## 20. 测试与验收

### 20.1 核心自动测试

- RFC 6238 SHA-1、SHA-256、SHA-512 固定向量；
- 6 位和 8 位输出；
- 30 秒及非默认周期；
- 标准 URI 默认值和显式参数；
- 非法算法、位数、周期、Base32 和 HOTP URI；
- 无真实账户的固定 Google Protobuf 样本；
- 单张、多张、乱序、重复、冲突、混批、缺页、取消和超时；
- HOTP、MD5、未知字段和损坏载荷分类；
- 现有账户与批次内部去重；
- 保存失败时的完整回滚；
- 旧账户和旧 v2 备份兼容。

### 20.2 Windows 集成验证

- 新版截图工具协议能力发现；
- 矩形截图成功、取消、过期和伪造回调；
- 截图期间超过 1 分钟后的重新解锁；
- 主实例响应路由且不创建第二个窗口；
- 剪贴板图片、无图片和非图片内容；
- PNG、JPEG、JPG、BMP 文件选择；
- 大文件、大像素图和损坏图片拒绝；
- 普通二维码和 Google 单张、多张的真实 ZXing 解码；
- 导入预览、分组选择和一次性保存；
- 浅色、深色、高对比度、键盘和屏幕阅读器文案。

### 20.3 完整验证

1. 运行 `LiubaiMfa.Core.Regression`。
2. 运行 Windows 平台和 CodeBehind 编译检查。
3. 执行 Windows 11 x64 Release 解决方案构建。
4. 启动实际 MSIX WinUI 应用。
5. 确认标题为“留白 MFA”的紧凑窗口可交互。
6. 完成至少一次截图、剪贴板、图片和 Google 多批导入演练。
7. 最终验证实例保持运行，除非用户要求关闭。

## 21. 完成标准

当且仅当以下条件全部满足，本功能才算完成：

1. 三个图片来源复用同一解码和验证规则。
2. 标准 TOTP 和 Google 单张、多张转移二维码可正确分类。
3. SHA-1、SHA-256、SHA-512、6/8 位和周期参数通过固定向量验证。
4. HOTP、MD5、未知及损坏输入被明确拒绝且不产生部分写入。
5. 批量导入为原子操作，保存失败保持原数据不变。
6. 截图回调不绕过自动锁定或 Windows Hello。
7. 不写日志、不持久化截图、不联网。
8. 核心回归、Release 构建和真实 MSIX 启动验证通过。
